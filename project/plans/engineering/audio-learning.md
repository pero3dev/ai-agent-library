# 音声学習機能の実現性検討と要件整理

作成日: 2026-09-13。状態: **要件 v0.1 確定・実装中**。Q1〜Q33 と全体確認への「OKです。実装に進んでください。」を反映しています。検討時点の候補・未実証事項は履歴として残し、後続の結果は [実装記録](../../records/2026-09-13/audio-learning-implementation.md)で追跡します。

ユーザー本人が iPhone で移動中に未読の記事を学べるよう、記事ごとの深い二人対話を日本語の AI 音声として公開サイトへ追加する案です。全記事を対象に、章などのまとまった単位で多数の記事を公開し、利用しながら改善します。制作は普段の Claude 利用を優先しつつ既存の Pro 契約と Windows PC を活用し、追加費用を抑えて公開まで自動化することを目指します。

## 目的と作業契約

AI Agent Library に、耳で学習するためのポッドキャストのような機能を追加できるか検討し、ユーザーとの対話で要件を詳細化します。

- 依頼範囲: 現行構成の読み取り、公式資料の確認、実現性判断、要件対話と記録まで。
- 所有ファイル: 本ファイル、`project/README.md`、`research/audio-learning-feasibility-2026-09-13.md`、`research/README.md`。
- 適用規約: [共通契約](../../../AGENTS.md)、[計画索引](../../README.md)、[調査・運用文書の規約](../../../harness/writing-rules.md#調査記録と運用文書)、[検証手順](../../../CONTRIBUTING.md#提出前のセルフチェック)。ROADMAP の「作業に応じた入口」に従うサイト拡張の新規検討です。
- 外部操作の許可根拠: 実現性検討の依頼に含まれる公式公開資料の読み取り。実装、音声生成の有料利用、アップロード、配信サービス登録、公開・GitHub 更新は今回の範囲に含めません。
- 必要な検証: `npm ci` 後の `npm run check`、記録の相対リンク・差分確認。サイトコード・依存・サンプルは変更しません。
- 各対話の終了条件: 実現できる範囲と未検証の制約を説明し、確定事項・質問と回答・残件を保存すること。初期の実現性判断は説明済みで、追加条件に応じて再評価しています。要件確定や実機検証の完了とは区別します。
- 要件定義全体の終了条件: 利用場面、学習内容、音声形式、再生・配信、制作・更新、予算、初期範囲、受入条件を対話で決め、ユーザーが合意した状態にすること。

## 初期の実現性判断

**事前に用意した音声をサイトで再生する方式は、現行の静的サイト構成に追加可能と判断します。** 根拠はソースの静的調査と公式資料です。音声生成や端末再生を実測した判断ではありません。[調査記録](../../../research/audio-learning-feasibility-2026-09-13.md)に根拠と未確認事項を残します。

初期検討では音声の内容と、音声を聴く場所を独立した選択として比較しました。以下は比較時の候補です。対話を経て Q3 で二人の対話、Q11 でサイト内再生を選びました。

| 内容の候補 | 学習体験 | 検討する点 |
| --- | --- | --- |
| 記事の読み上げ | 記事に沿って聴く | 図・表・コード・リンクをどう伝えるか |
| 一人の講義・解説 | 耳で理解しやすい順序に組み直す | 深さ、具体例、振り返り、原文との対応 |
| 二人の対話 | 聞き手の疑問と解説者の回答で進める | 掛け合いの量、冗長さ、専門性、正確さ |

聴く場所の初期候補は、サイト内再生、音声ファイルのダウンロード、外部ポッドキャストアプリへの配信でした。Q11・Q13 を経てサイトでの通信ありの再生を採り、外部配信や完全オフライン対応は現行要求に含めません。

制作工程の候補は「既存記事 → 音声用台本 → 内容確認 → 音声化 → 音声確認 → サイトへ配置」です。Q19 で制作から公開までの自動化を希望されたため、毎回のユーザー確認を前提にせず、各工程で自動確認する内容・失敗時の扱い・例外時の確認者を設計します。生成と配信を分けることで、公開サイト上で毎回音声生成を待たずに再生できます。生成サービスと自動化の実行環境は未選定です。

無料優先・全記事という条件を踏まえた構成候補は、台本を既存の Claude Pro に含まれる Claude Code で制作し、Windows PC 上の VOICEVOX 系などで音声化し、音声ファイルを GitHub Releases 等から配信する方式です。サイト本体は現在の静的構成を活かします。Claude の契約枠・PC の処理時間・音質・配信と iPhone の実動作は未検証のため、無追加費用で全要件を満たすと確定した判断ではありません。詳細と条件付きの代替候補は調査記録を参照してください。

## 順に対話で決めること

1. 利用者と利用場面: 自分用か一般公開か、端末、移動・家事・着席、画面を見られるか。
2. 学習目的: 初めて学ぶ、復習、全体像をつかむ、実務判断を深める。現在の知識と到達したい状態。
3. コンテンツ設計: 読み上げ・講義・対話、記事単位・テーマ横断、長さ、難易度、シリーズ順序。
4. 聞き心地: 声、人数、話速、専門用語の読み、間、BGM、繰り返しや小問の要否。
5. 再生体験: 連続再生、倍速、巻き戻し、途中再開、ロック中の操作、他ページ閲覧、通信断、オフライン。
6. 記事との連携: 台本、章立て、元記事へのリンク、聴取済み管理、更新前の音声の扱い。
7. 制作と更新: 対象範囲、制作担当、生成方式、費用、公開前の確認、記事更新の検出と再生成。
8. 公開と初期範囲: 公開対象、サイト内・外部配信、初期エピソード数、優先機能、実機受入条件。

一度に全項目を質問せず、回答を踏まえて少数ずつ掘り下げます。提案・確定・未決を区別し、未回答を承認とみなしません。

## 要件案をまとめる際の補足提案

以下は確定事項から導いた設計・受入の案です。ユーザーの発言そのものとしては扱いません。

| 論点 | 提案 | 確認すること |
| --- | --- | --- |
| 音声化の対象 | `docs/` の front matter が `status: published` の学習記事を対象にする。draft 記事・セクション README・GLOSSARY・計画や運用文書は含めない | 2026-09-13 の該当記事は 199 本。新規記事は published になった後に対象へ加える。この境界を全体確認する |
| 台本の密度 | 元記事の主要論点、設計理由、条件・例外、失敗例を残し、前提の説明を補う。リンクや記号を機械的に全部読む尺は作らない | 記事と台本の対応を自動検査・独立した内容確認で評価する |
| 声の一貫性 | 聞き分けやすい 2 種を仮選定し、役割と声を固定する。略語・製品名・コード名の読みを管理する | 聞き取りにくい声や読みは利用後に変更できるようにする |
| 自動確認 | 台本の論点・根拠の対応、発話の脱落・重複、話者、音声ファイルの生成完了、長さ・無音・頭出し情報を確認する | 自動確認で検出できない自然さや意味の誤りもある。試験方式ごとの限界を記録する |
| 版の整合 | 元記事・台本・音声・声設定を版で結び、新版が完成して検査を通るまで旧音声を保持する | 再生成中にさらに記事が変わった場合に古い候補を最新として公開しない |
| 再生位置と差し替え | 再生中の音声を途中で新版へ入れ替えない。新版で章・長さが変わった場合、旧版の秒数を無条件に引き継がない | 章対応による再開か再開位置のリセットかを具体化する |
| 一覧と操作 | 音声一覧に記事名・長さ・章・更新日を表示し、再生リストへの追加・削除・並べ替えを行えるようにする | 記事画面からも再生でき、サイト内のページ移動で再生が途切れない |
| 課金と実行枠 | 契約枠を超えたら状態を保存して待機し、有料 API や追加 credits へ自動切替しない | 普段の Claude 利用を優先し、制作時間帯に指定なし。具体的な頻度・制作量を設計する |

### 全体確認に含める内容の合格条件案

- 元記事の主要論点・設計判断とその理由・成立条件・重要な例外・失敗例を台本で扱うこと。参考 URL の読み上げや重複する案内の逐語再現は求めません。
- 図・コードは処理順序、分岐、入力・出力、制約、エラー時の振る舞いを言語化し、判断に必要な識別子・設定値を落とさないこと。
- AI の前提知識を必要な分だけ補足し、たとえ話を事実や元記事の実例と混同しないこと。未確認の仕様や根拠のない断定を台本へ追加しないこと。
- 二人の役割と声が一貫し、発話の欠落・重複や途中の切断がなく、聞き手の要約と最後のまとめがあること。
- これらの自動確認が通らない記事は公開せず、REQ-037 に従って修正・保留すること。検査を通ったことだけで内容や音質の完全性を保証したと表現しないこと。

これらは元記事に近い深さでの初回学習と、自動公開を両立するための具体案です。対象境界と併せて要件案全体の確認に含めます。数値閾値・検査ツール・再試行回数は実装設計時に決め、実際に実行した方式と結果を区別して記録します。

実装後の主な再生受入は、指定の iPhone/Safari/AirPods での画面ロック・他アプリ使用中の長時間再生、ロック中の次エピソードへの移行、途中再開、倍速、15 秒移動、章の頭出し、通信断・着信等の割込み後の復帰です。実機を使わない静的検査・Chromium 試験のみで合格とは扱いません。

音声を聴いて内容の問題を指摘する導線、元記事が非公開になった際の扱い、重大な誤りが判明した音声の停止・修正方法も、運用案に含めます。一般的な記事更新時の旧音声継続(REQ-028)とは状況を区別します。

## 対話記録

### Q1: 利用者・端末・利用場面

質問: 主に誰が、どの端末で、どんな場面で聴く想定ですか。例として「自分が iPhone で通勤・散歩中に、画面を見ずに聴く」。

回答: 「主に自分がiPhoneで通勤中や散歩中に画面を見ずに聴くのを想定しています。」

反映: REQ-004・005。耳だけで理解できる説明と、画面ロック中の再生を重点検討します。Q1 時点で未確定だったオフライン・連続再生・外部アプリは Q11〜14、具体的な端末・ブラウザーは Q26 で確認しました。

### Q2: 学習目的

質問: 音声で初めて学ぶこと、既習内容の復習、両方のうち、主な目的はどれに近いですか。

回答: 「まだ読んでいない内容を、音声で初めて学びたい」。

反映: REQ-006。元記事を読んだ前提を置かず、用語や具体例の補足を検討します。この回答だけでは確定しない知識水準・深さは、後続の Q4・Q5 で確認しました。

### Q3: 音声の形式

質問: 聞き手と解説者の二人の対話、一人の講義、形式を固定せず理解しやすさを優先、のどれが理想に近いですか。好きな番組や避けたい話し方があれば教えてください。

回答: 「二人の対話：聞き手が疑問を投げかけ、解説者が答える」。

反映: REQ-007。声の性別・雰囲気、掛け合いの量、話速、AI 音声生成サービスの採用までは未確定です。

### Q4: 理解の到達点

質問: 一つのテーマを聴いた後、実務の使いどころ・選び方・注意点を判断する深さ、全体像と用語を説明する深さ、元記事に近い密度で実装・設計の細部を理解する深さ、のどれを目指しますか。

回答: 「実装の仕組みや設計の細部まで、元記事に近い密度で理解できる深さ」。

反映: REQ-008。実装の流れ・設計理由を音声で説明することを検討します。図・コードの扱いは Q8 で確認しました。理解の受入条件は未確定です。

### Q5: 前提知識

質問: 普段の仕事と AI・AI Agent の経験を教えてください。開発経験、AI ツールの利用経験、仕組みの理解などが説明の出発点になります。

回答: 「バックエンド/フロントエンドの開発経験は3年ほど、Copilotは使い、LLMやRAG、MCPの仕組みはまだ曖昧」。
