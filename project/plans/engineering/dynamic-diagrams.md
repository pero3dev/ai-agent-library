## 2. 対象と「全対応」の定義

### 2.1 対象集合

対象の正本は `docs/<章>/<記事>.md`。`status: published` の学習記事を数え、各章の `README.md` は区別する。作成日の全件と章別件数は[棚卸し付録](dynamic-diagram-inventory.md)に固定する。記事の抽出に使う状態と、図解の制作状態を混同しない。

2026-09-24 の基準は16章・199記事、全記事が `published`。`docs/` の Markdown 215ファイルとの差分は章の索引16本である。既存の Mermaid は73記事に74ブロックあり、読書に連動する専用図解はTransformer記事の自己注意節に導入されている。棚卸し時の基準 commit は `ef8e9a9e27a427f9daa0a62226731adf15c5a1e2`。

GLOSSARY、章の索引、ホーム、検索、学習ロードマップの専用ページ、音声一覧、サンプルの README、運用・調査文書は「支援ページ」として別管理する。`docs/00-overview/learning-roadmap.md` など、入口の役割を持つ学習記事は対象から外さない。既存の依存グラフや Mermaid の拡大機能は資産として使うが、それだけで読書連動図解の対応済みとは数えない。

初期の完了判定には作成日の対象集合を使う。導入中に追加・削除・非公開化された記事は差分を別に記録し、最終時点の公開記事集合とも照合する。将来の新規記事に同じ制作工程を組み込む運用は本計画の提案とする。

### 2.2 対応完了の条件

記事ごとに次をすべて満たした時点で、動的図解に「対応完了」とする。

1. 主題を説明する主図解を最低1つ持ち、読む段落と図の状態が対応している。
2. 記事の主要論点を一覧化し、図解で扱う場所、本文・既存の表で十分な場所、その理由を絵コンテに記録している。主図解1つで足りなければ、節ごとに図解を追加する。
3. 関係・処理・比較・条件のうち、その記事で理解に必要な要素が、停止した図でも読み取れる。
4. 内容レビュー、見た目と操作、静的検査、ブラウザー試験、公開確認が、その版に対して完了している。
5. 本文との対応が最新で、未解決の重要な欠落・誤りがない。

この条件で、対象記事の対応完了率を100%にする。主要論点の割当率も100%とし、未検討の論点を「本文のみ」として埋めない。参考文献・リンク集・操作コマンドの全行を動かすことは完成条件に含めない。付録の図解候補は絵コンテの入口であり、それだけで記事全体の設計が完了した意味ではない。

自己注意は1記事内の1節に公開済みの基準作がある状態。Transformer 記事全体の論点網羅については、上の完成条件で改めて判定する。

## 3. 読書体験の設計

### 3.1 基本の体験

PC の広い画面では、本文の隣に図を固定表示する。段落を読み進めると、同じ物体や矢印が次の状態へ移り、どこが変わったか分かる。スクロール量を時間へ機械的に割り当てず、段落と意味の区切りに合わせる。ページ自身が読者を強制的にスクロールさせる操作は設けない。

読者は「再生」「一時停止」「前へ・次へ」「時間バー」「拡大」「本文に連動」を共通の位置で操作できる。手動操作中は図だけを進め、読書へ戻すと現在の本文位置に合う図へ戻る。再生は読者が開始し、画面外や非表示タブで止める。新しい図を読むたびに操作を学び直す必要がないようにする。

狭い PC 画面・タブレット・スマートフォンでは本文と図を縦に配置する。図の可読性を保ち、拡大表示でも必須操作が画面から欠けないようにする。全記事で横並びを強制せず、最適な切替幅を基準作で決める。

現行の自己注意では、広い画面で対象記事の目次を隠して図解幅を確保している。全記事への展開時は、図解節の幅と記事全体の移動手段を一緒に設計する。目次へのアクセスを残す方法をP0で比較し、記事の長さにかかわらず現在位置と次の節が分かるようにする。

### 3.2 図解の質をそろえる約束

| 観点 | 制作時の約束 |
| --- | --- |
| 動きの意味 | 状態・情報・責任・値の変化を表す。各遷移が何を理解させるかを絵コンテに書く |
| 視線 | 1場面の中心となる変化を絞り、関係する要素を同じ視野に置く |
| 連続性 | 同じ要素の位置・形・名前を保つ。配置を変える場合は移動先が追えるようにする |
| 読みやすさ | 図中文字は本文の用語にそろえ、補助ラベルを短くする。色だけで意味を区別しない |
| 密度 | 全体を一度に出さず、読んでいる論点に合わせて詳細を見せる。全体像へ戻れる入口は保つ |
| 正確さ | 数値は同じモデルから計算する。概念図・説明用データ・実測値・製品固有の仕様を表示上も区別する |
| 抑制 | 動きを減らす設定では遷移を省いても同じ情報を提供する。点滅や常時ループを学習の前提にしない |
| 文章量 | 本文の複製、長い追加解説、新しい例題を増やさない。必要な操作名と図のラベルに留める |

量産前に、数値・フロー・比較の3種類を品質の基準作として保存する。全記事に同じ完成条件を適用し、基準作の見た目だけを特別に作り込む運用にはしない。

### 3.3 記事に合わせる7つの図解型

| 型 | 読者が確かめること | 主な表現 | 対象例 |
| --- | --- | --- | --- |
| 数値 | 値がどの演算で変わるか | 行列、重み、ベクトル、分布の段階表示 | 自己注意、トークン生成、スケーリング則 |
| フロー | 何がどの順序で渡るか | 情報の移動、分岐、待機、反復 | Agent ループ、Tool Use、RAG、MCP |
| 時系列 | いつ起き、どこで戻るか | 実行履歴、並列処理、失敗と回復 | リトライ、チェックポイント、評価軌跡 |
| 構造 | どの範囲が誰の責任か | 層、境界、入れ子、部分の展開 | コンテキスト、ハーネス、権限分離 |
| 比較 | 条件が変わると差がどこに出るか | 同じ配置での切替、並列比較、差分強調 | Workflow と Agent、設計方式、評価方式 |
| 判断 | どの条件が判断に関係するか | 条件の選択、依存関係、判断過程の強調 | 導入判断、承認設計、運用上の選択 |
| 地図 | 概念・主体・参照先がどうつながるか | 関係図、経路の強調、対象領域の絞り込み | 学習順、規制の確認先、組織・業界 |

型は制作用の分類であり、全記事へ同じ見た目を適用する規則ではない。組み合わせも認める。比較や判断に架空の点数・推奨順位を追加せず、法務・規制の記事では本文にある確認先と検討手順を図示する。適法性や採用可否の判定器にはしない。

### 3.4 動画の位置づけ

初期は、読書位置・停止・段階移動に直接対応できるコードによる図解を優先する。時間的な動きが重要な記事では、同じシーン定義から短い無音動画を書き出す方式を検討する。別の動画台本や追加ナレーションを必須にしない。

動画を追加する場合も本文連動の操作を残し、ポスター画像・字幕または同等のテキスト・静止表示・容量と遅延読み込み・記事更新時の再生成を受入に含める。外部の動画生成サービスや有料 API は前提にしない。

## 4. 実装の構成案

### 4.1 現行資産をどう使うか

現行の根拠は[サイト README](../../../website/README.md#本文に連動する動的図)、[自己注意の実装](../../../website/components/attention/attention-walkthrough.jsx)、[数値モデル](../../../website/lib/attention-model.mjs)、[本文装飾](../../../website/lib/attention-decoration.mjs)、[MDX ガード](../../../website/lib/mdx-safety.mjs)。自己注意の制御と表示は記事専用であり、共通化の実装はまだ行っていない。

| 層 | 共通化するもの | 記事ごとに持つもの |
| --- | --- | --- |
| 読書と操作 | 本文位置の検出、読書・手動・再生の状態管理、停止、段階操作、時間バー、拡大、縮小モーション | 本文のどこがどの場面に対応するか |
| 視覚表現 | 配色・文字・余白、ノード・線・帯・行列・境界、強調と遷移の基本部品 | レイアウト、情報量、変化の演出、補助ラベル |
| 意味とデータ | シーンの登録形式、値の検証、出典・説明用データの区別、版管理 | 数式・処理モデル、条件、段階ごとの意味 |
| 生成と検査 | Markdown AST への包装、対象照合、MDX 許可表、網羅率集計、静止表示の生成 | 対象記事・節、本文との対応定義、個別の検証条件 |

最初に既存の自己注意を同じ動作のまま共通外枠へ移し、その後で別形式へ拡張する。本文は `docs/` に一度だけ置く。生成される `website/content/`・`generated/`・`out/` を手で編集しない。図解定義に本文を丸ごと持たせない。

自己注意固有の6段階や4位置を共通APIの前提にしない。任意時点の表示を同じモデル状態から再現し、数値・式・ラベル・強調の段階判定をそろえる。逆方向への操作や段階途中へのシークでも矛盾が生じない設計にする。

### 4.2 図解の登録と本文対応

新設する登録台帳の候補は `website/diagrams/registry.json`。以下は新規提案であり、現在存在する API・ファイルではない。

| 項目 | 用途 |
| --- | --- |
| `id` / `article` / `section` | 図解の安定 ID、記事パス、対象見出しを識別する |
| `sourceDigest` / `schemaVersion` | 対象本文の版と登録形式を識別する |
| `sceneModule` / `modelModule` | 許可された描画・意味モデルを結び付ける |
| `steps` / `sourceMap` | 場面と既存の段落・式・表・コード範囲を対応させる |
| `staticFallback` / `contentKind` | 静止表現と、概念図・説明用データ等の区分を持つ |
| `status` / `reviewedDigest` | 制作段階と、内容レビュー済みの本文版を記録する |
| `evidence` | 検証対象の版、結果、公開確認の記録を参照する |

パスや component 名は登録済みの候補へ限定する。Markdown から任意の import・属性式・スクリプトを実行できる入口を増やさない。MDX の許可表と試験は新しい包装要素の追加と同じ変更で更新する。

対象節の本文・式・表を正規化してダイジェストを作り、見出しの一意性・範囲・順序と併せて照合する。記事全体の版も記録するが、無関係な参考リンクの変更だけで全シーンを再制作しない。本文が同じ構造のまま事実だけ変わった場合も、対象節のダイジェストでレビューを要求できるようにする。

### 4.3 性能と障害時の扱い

記事に必要な図解だけを読み込み、図の領域を先に確保する。全記事のシーンや重い描画ライブラリを共通バンドルへ載せない。SVG・HTML を基本とし、大規模な描画が必要な場合だけ別方式を実測して採否を決める。停止中は連続した描画ループを残さない。

初期の性能目標案は、図解による追加の圧縮 JS を共通部100 KiB・記事固有部75 KiB以内、図解に起因する CLS を0.05以下、操作への画面応答を200 ms以内、代表 PC で再生中の95パーセンタイルのフレーム間隔を32 ms以内とする。いずれも測定済みの実績ではない。P0で環境・測定方法・既存サイトとの差分を固定して、実現性を確かめたうえで採択する。

初回読み込み中、図解の JavaScript が失敗した場合、JavaScript 無効時、印刷時にも本文を読めるようにする。図解は静止表示と短い説明を利用できる構成を目指し、静止表示だけで情報が不足する図には主要段階の静止一覧を用意する。短い説明は原文の要約・図の代替説明に限定し、新しい論点や具体例を追加しない。

## 5. 制作と展開の順序

### 5.1 導入波

導入順は「共通基準の検証 → 原理 → Agent の中核 → 実装・品質・運用 → 応用・判断 → 全体受入」。学習記事の既存の執筆フェーズとは別の、表示機能の導入順である。記事別の仮割当は[付録](dynamic-diagram-inventory.md)を正本とする。

| 段階 | 主な対象と作業 | 次へ進む条件 |
| --- | --- | --- |
| P0 基盤と基準作 | 自己注意から共通外枠を抽出。Agent ループ、Workflow と Agent の比較で異なる型を試す。登録・静止表示・版管理・試験の最小セットを作る | 3種類が同じ操作・品質基準を満たし、既存自己注意の退行なし。制作時間・性能を実測 |
| P1 原理と内部構造 | 11 LLM 内部構造、10 LLM 基礎。Transformer 記事の残る主要論点、注意変種、MoE、生成・トークン・学習へ進む | 対象記事の主要論点と図の対応、数値・概念の区別、数式・表示の受入完了 |
| P2 Agent の中核 | 00 概要、01 概念、02 アーキテクチャ、08 コーディングエージェント | ループ・ツール・メモリ・委譲・コンテキスト等の用語と視覚表現が記事間で一貫 |
| P3 実装と運用品質 | 03 実装、04 評価、05 運用、06 セキュリティ | 正常系だけでなく本文にある失敗・再試行・境界・承認・観測を表現し、製品固有の仕様を照合 |
| P4 応用と判断 | 07 ケーススタディ、09 ビジネス、12 マルチモーダル、13 ドメイン、14 UX・プロダクト、15 人と AI | 関係・比較・判断の図解を完成。制度の断定や架空の数値を追加せず、本文の条件を保持 |
| P5 全体受入と運用移行 | 対象一覧との突合、記事横断の統一、支援ページ、表示性能、更新時の試行、公開確認 | 対象記事の対応完了率100%、主要論点の割当率100%、未解決の重要な不具合0件 |

初期対象の内訳はP1が15記事、P2が54記事、P3が78記事、P4が52記事で、合計199記事。P0・P5はこの集合に対する共通作業で、別の記事数として加算しない。

P0で先行する記事はP2にも属するが、集計は記事IDで一度だけ数える。各波の最後に独立レビューと公開確認を置く。波の途中も検証済みの制作単位で公開できる計画とし、各単位の対象と公開権限は実装開始時の作業契約に記録する。

P0は小さな共通基盤を実物で確かめる段階とする。7種類すべての描画機能を先に実装する必要はなく、採用する記事が現れた時点で部品を追加する。

### 5.3 1制作単位の進め方

1. **原文を読む**: 2〜3記事の主題・既存の式・図・表・出典を確認し、主要論点を抽出する。
2. **絵コンテを作る**: 図にする範囲、段落対応、各状態、状態間で変わるもの、静止時の姿を決める。
3. **意味を確認する**: 数値なら不変条件、手順なら遷移条件、判断なら本文の条件と例外を確認する。
4. **実装する**: 共通外枠と部品を使い、記事固有の配置・モデル・ラベルを作る。
5. **検証する**: 自動検査に加え、読み進めて理解できるか、操作が読書を妨げないかを独立レビューする。
6. **公開して確認する**: 許可された制作単位の PR・CI・Pages・公開ページを照合し、対象版と結果を残す。

担当を分ける場合、共通基盤の変更担当を1つにし、記事別担当には固有シーン・登録定義・固有試験の所有範囲を渡す。共通部の変更が必要になったら調整し、他の担当の変更を巻き戻さない。

### 5.4 工数と進捗の扱い

全記事の高品質な図解は継続制作として扱う。公開済み1節の速度を全記事へ掛け合わせた納期は置かず、P0と最初の5記事で、絵コンテ・実装・修正・検証・公開に分けて時間を記録する。

199記事を2〜3記事ずつ扱うと、記事制作だけでおおむね67〜100単位の規模になる。P0で先行制作した記事はその数に含め、既存自己注意の再利用分は個別見積もりで減らす。多数の記事に同時着手する前に、共通部の変更とレビューの待ち時間を把握する。

その実測から、図解型別の残記事数と中央値で残工数を算出し、図解数が多い記事と新しい型の制作を別に見積もる。作業者数、並列化できる記事、共通基盤の変更、レビュー待ちを加味して予定を更新する。制作単位は原則2〜3記事で、数値モデルや複雑な図解は1記事単位も認める。

進捗は「対象確定 → 絵コンテ済み → 実装済み → 検証済み → 公開確認済み」で記録する。記事の公開状態は既存の front matter、図解の状態は専用台帳を正本にする。PRがあること、図が表示されること、公開確認済みであることをそれぞれ区別する。

## 6. 品質と受入

### 6.1 全記事に共通の合格条件

| 領域 | 合格条件と証拠 |
| --- | --- |
| 原文との一致 | 本文・式・表・リンク・見出し・アンカーの保持を機械照合。主要論点との対応を独立レビュー |
| 意味の正確さ | 数値の不変条件と境界値、手順の分岐と終了、比較条件の同一性を検証。本文の根拠を超える主張がない |
| 学習としての質 | 各場面が何を示すか、遷移で何が変わったか、本文のどこに対応するかを、担当外のレビュー者が説明できる |
| 表示 | 1280・1440・1920px のPC幅を中心に確認。1280×720pxの低い画面、768・390px幅も確認し、必要なラベル・操作・本文に重なりや欠けがない |
| 色と文字 | 明暗両テーマ、200%拡大、色に依存しない識別。細かい文字を拡大操作だけで救済しない |
| 操作 | 読書同期、逆方向スクロール、再生・停止・戻る・シーク、拡大、本文同期への復帰、直接アンカー移動が整合 |
| アクセシビリティ | キーボード、フォーカス、ダイアログ、支援技術用の名称、動きを減らす設定、読み上げ可能な静止説明を確認 |
| 回復性 | JS無効・読込失敗・印刷でも本文を保持。複数図解の状態・ID・スクロール監視が干渉しない |
| 性能 | P0で採択した性能予算を満たし、非表示中の連続再生がない。記事単位で必要な資産だけが読み込まれる |
| 公開 | PRの対象版、必須CI、マージ、main CI、Pages配信、公開ページの操作を照合 |

レビューでは、自動試験に通ることと理解しやすいことを別に判定する。「動くが読み取れない」「図だけでは論点が分からない」「本文と違う用語を使う」は修正対象とする。

### 6.2 検証を全記事へ広げる方法

全対象へ、登録・本文対応・静止表示・表示開始・主要操作・コンソールエラーの検査を自動生成する。固有の意味モデルは記事ごとに検証し、共通操作の詳しい回帰試験は基準作と新しい型を中心に行う。新しい記事も、キーとなる段階遷移と読書への復帰は省略しない。

各制作単位で `npm ci` と `npm run check`、サイトの単体試験、公開条件の静的ビルド、該当記事と共通基盤のブラウザー回帰を実行する。共通部を変更した場合は影響する全記事へ広げる。P5では全記事のスモーク試験と、全7種類・主要な境界条件の回帰を Chromium／WebKit で行う。

初回読み込みが遅い状況では、フォント・数式・Mermaid等の準備を待って操作試験の基準位置を確定する。準備前の試験も別に持ち、ページ全体の `scrollY` だけでなく本文の画面内位置を測って、読み込みによる高さの変化と意図しない読書位置の移動を区別する。時計を制御する試験は、操作開始時刻と実時間の混入を明確にする。

WebKitによる自動試験、実機Safari、スクリーンリーダーによる操作、ユーザー本人の学習体験は証拠を分ける。P0でキーボードと利用可能な実機の支援技術を使って共通外枠を受入し、未実施の環境は明示する。PC中心の要件でも、既存のモバイル閲覧・数式・音声機能を退行させない。

## 7. 更新・運用・復旧

本文更新時は対象記事と対象節の版を比較し、影響する図解を「再確認が必要」にする。図解の本文対応が崩れた場合や、意味の変更が未レビューの場合は公開候補の検証を止める。定期最新化へも図解への影響確認を組み込み、確認済みの本文と図解を同じ公開物に載せる。

急ぎの本文訂正を先に公開する必要がある場合は、その図解を明示的に無効化して本文のみを公開できるようにする。古い静止画像も同じ意味の変更を受けるため、未確認のものを代わりに表示しない。対象は対応完了の集計から外し、復旧タスク・理由・影響範囲を残す。無効化を暗黙の成功や恒久的な除外にしない。

共通基盤の変更時は、図解型別の代表と影響記事を再検証する。問題のある記事は個別に無効化・復旧できる設計にし、全記事の公開を巻き戻す判断が不要になるよう範囲を限定する。公開物と対応する commit・レビュー・検証結果を保存する。

将来の記事追加時は、記事の主題と同時に図解候補を台帳へ登録する。導入中の新規記事を見逃さない差分検査、図解付き記事の一覧、型別の共有資産、再確認待ち一覧を維持する。定期実行や自動公開の設定自体は別の実装作業として扱う。
