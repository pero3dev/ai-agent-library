## 3. 「すべて復元可能」の具体的な意味

復元を次の三つに分け、それぞれの成功条件を持たせる。

1. **保存時のソースと作業状態の復元**: コミット履歴、四つの保存点、元HEAD、追跡ファイルの変更・削除、未追跡の制作物、必要な既存補助ファイルを元の相対パスで取り出せる。本文、図の意味モデル、登録情報、専用試験、lockfileと実施記録が揃う。現在のステージ状態も記録する。
2. **廃止前の表示の再現**: 最後に公開成功したPages出力と、ローカルの199記事分の出力を区別して保管する。静的出力はビルド依存の再取得が難しくなっても図を見るための保存物であり、編集する正本にしない。
3. **将来のサイトへの再導入**: 保存したソースをその時点のmainへ必要な範囲で再導入し、本文との対応と必要な検査を取り直す。将来変更された記事へ古い登録を強制適用しない。

ソース復元は、GitHubのPRを同じ番号・同じ審査状態で作り直すことや、失敗している依存監査を成功に変えることではない。外部サービスの永続性を復元成功条件にせず、必要な保存物は私有バックアップから取得できる構成にする。

## 4. 推奨するバックアップ構成

元の作業ツリーを変更せず、隔離した保存用コピーからまとめる。保存のために未提出のP4/P5をmainへマージしない。

| 保存物 | 内容 | 確認方法 |
| --- | --- | --- |
| `source.bundle` | 四つの保存点と、それらに到達する完全なGit履歴。最新制作状態は隔離コピー内で保存用commitにし、必要な未追跡ソースも含める | `git bundle verify`、元リポジトリに依存しない空フォルダでのclone、保存点のcheckout |
| `workspace-support.zip` | 元HEAD・branch・status、追跡差分のbinary patch、index差分、未追跡制作物の元の区分、既存の補助スクリプト・log・画像・制作記録。ルートとwebsiteの作業補助も必要範囲を含める | 展開確認と保存元の内容比較。削除された追跡ファイルも再現できることを確認 |
| `site-last-published` | PR #140で公開成功したPages成果物を、commit・CI番号と対応づけて保存 | 正しいbase pathでローカルHTTP表示。元の取得物を展開して使用 |
| `site-local-working` | ローカル最新制作状態に対応する静的出力。最新ソースと一致しない既存出力は一致済みと扱わない | ソースの保存点とbuild結果を対応づけ、代表図を表示 |
| `RESTORE.md` | 保存点、保存対象と除外対象、使用環境、環境変数、復元・表示・再導入手順、実施結果と未確認事項 | 別の絶対パスから手順だけで復元できるか確認 |

Git bundleはindex・作業ツリー・リポジトリ設定などを保存しないため、これらをbundleだけに任せない。[Git公式のbundle仕様](https://git-scm.com/docs/git-bundle)を根拠に分ける。増分bundleではなく、元cloneなしで復元できる完全なbundleにする。

公開成功したrun 37082303797には、今回の読み取り時点で未失効の `github-pages` artifactがある（42,409,133 bytes）。保存実施時に取得可能性を再確認する。artifactに保存期限があるため、GitHubのrunへのリンクだけをバックアップにしない。

### 含めるもの・除外するもの

- ソースの保存用commitには図解だけでなく、その保存点の `docs/`、サイトの共有実装、設定、lockfile、必要な試験・fixtureも含める。図解部品だけでは元の本文との対応を再現できない。
- 隠しファイルと日本語・長い相対パス、binaryファイルを保存できる形式と方法を使う。ZIPに入ったことだけで成功にせず、実際に展開する。
- `.git` ディレクトリの丸ごとコピーを移植用の正本にしない。音声学習の別worktreeが登録されており、Gitのリンクworktreeは共通Gitディレクトリを参照する。[Git公式のworktree仕様](https://git-scm.com/docs/git-worktree)に従い、復元先は独立したcloneにする。
- `node_modules/`、`.next/`、通常の生成content・検索索引をソースの保存用commitへ入れない。公開用・ローカル用の静的出力は上の別保存物へ置く。
- `.env`、認証情報、ユーザー個人のGitHub/Codex設定は動的図解の復元に不要であり、この機能バックアップへ混入させない。必要な変数名と非秘密の設定値をRESTOREへ記載する。
- 保存用の追加ハッシュ台帳や全ファイルの手書き記録を作らない。Gitのオブジェクトと復元後の内容比較、アーカイブの展開検査を使う。

### 依存環境の保存範囲

lockfileだけで将来の完全オフラインビルドまで保証しない。RESTOREに実測のNode/npm/Gitと使用OS、CIのNode設定、静的出力用の `STATIC_EXPORT=1` と `NEXT_PUBLIC_BASE_PATH=/ai-agent-library` を記録する。

ユーザー回答で、完全なソース・作業状態の復元と保存済みサイトの表示再現を対象に決定した。完全オフライン再ビルド用のruntime・依存パッケージの保存は今回の対象外。編集と再ビルドでは、記録した環境とlockfileを使って必要な依存を取得する。あるPCのnode_modulesコピーだけを別PCでの再現方法にしない。

## 5. 削除前の復元確認

以下が揃うまで機能削除へ進まない。

1. ローカルバックアップを元リポジトリと異なる場所へ作成し、保存用コピーで四つの保存点を確認する。
2. 元cloneへ依存しないフォルダへbundleからcloneし、最新制作状態のソースを比較する。元HEADへの差分と未追跡区分を使って、元の未提出状態も再構成できることを確認する。元作業ツリーのbranch・HEAD・差分を変えない。
3. 必要な依存を準備し、最新制作状態の静的buildと登録・本文対応の検査、代表7型の表示・主要操作を確認する。199記事の制作検査を一から全部やり直すことを保存手順の目的にはしない。保存点と再現結果を区別して記録する。
4. 最後に公開成功した静的出力を、公開時と同じbase pathでHTTP表示する。ローカルの199記事分の出力と取り違えない。
5. 私有ストレージへ保存物をコピーし、そこから別フォルダへ取得する。bundleの検証、アーカイブの展開・内容比較と必要な表示を確認する。ローカルコピーだけからの成功を私有ストレージの復元成功にしない。
6. RESTOREへ確認結果を短く記録する。作成・コピー・取得・復元のどこまで実施したかを区別する。

元状態のindexは今回0件だが、実施前に変わっていればindex差分も保存する。source.bundle内の保存用commitにまとめた状態と、元の未コミット状態を混同しない。

## 6. 機能削除の対象

削除は、その時点の最新mainから作る隔離した作業ツリーで行う。元の199記事分の制作ツリーをclean・reset・一括stageして削除作業へ転用しない。長期間の機能追加を一括revertしてサイト全体を古い版へ戻す方法は使わず、現行mainから対象機能を取り除く。

| 対象 | 削除・変更すること | 残すこと |
| --- | --- | --- |
| 図の描画と操作 | 動的図解専用の `components/diagrams/` 部品・CSS、ReadingFigure、読書同期、時計、再生、シーク、拡大、図解専用の印刷とnavigation | 別機能が参照する共有部品があれば用途を確認して残す |
| 各記事の意味モデル | 専用model・bindings・sceneと図の段階データ | 本文と記事内の既存例、原文の式・表・図 |
| 登録と網羅情報 | `website/diagrams/registry.json`、`articles.json`、専用の登録・本文対応・受入モジュール | 通常の記事メタデータ・記事の公開状態 |
| 本文への自動挿入 | `diagram-decoration.mjs` と `attention-decoration.mjs`、`doc-decorations.mjs` からの図解呼び出し、`sync-content.mjs` の図解metadata生成・検査 | TODO、用語リンク、練習節の既存装飾と通常のcontent同期 |

| テスト・測定 | 動的図解専用unit/browser、網羅検査、性能測定。共通試験内の専用assertionは対象部分を取り除く | 記事・検索・keyboard・Mermaid・音声・ロードマップの試験 |
| 依存とCI | 専用の依存だけを用途確認後に削除。CI内の専用処理があれば更新 | 必須CI・依存監査。Mermaid・KaTeX・ReactFlowを名前だけで削除しない |

`@xyflow/react` は `website/components/roadmap/dependency-graph.jsx` で使われている。動的図解の廃止を理由に削除しない。Mermaidは記事内の既存図に必要であり、表示機能を残す。

生成物を直接編集しない。正本と同期処理を変更してクリーンビルドし、古い図解MDX・metadata・chunkが出力へ残らないことを確認する。過去の制作記録に図解への言及が残ることと、サイトから図解が再挿入されることを分ける。

## 7. PR・検証・公開の進め方

実施を依頼された場合の順序は次のとおり。今回、これらの外部操作は実行しない。

1. バックアップと二か所からの復元確認を完了し、保存物を上書きしない状態にする。
2. PR #142を保管済みの未マージ成果として閉じる。保存のためにマージしない。リモートbranchの削除は必須にしない。
3. 最新mainから機能削除の通常PRを一つ作る。150記事の既存編集であり、新規記事1〜3本の制作単位へ分割する必要はない。
4. rootとwebsiteの `npm ci`、`npm run check`、サイトunit、公開相当のクリーンbuild、必要なbrowser検査を実行する。Git形式検査と必須9 CIを確認する。
5. 対象機能の消失と残す機能の維持を確認してsquashマージし、main CIとPagesの成功を確認する。
6. 公開後は表示確認だけを行う。廃止記録へバックアップの論理的な保存先と復元手順の入口を残し、私有ストレージの認証情報や共有用secretを公開しない。

### 削除PRの受入条件

- `docs/` の本文、front matter、具体例、式、表、Mermaidコードに差分がない。記事の確認日・公開状態を機能廃止のために更新しない。
- 全記事の生成MDXに動的図解専用要素が残らない。通常の見出し・anchor・本文順と目次が維持される。
- 新しい静的出力に動的図解の操作UI、専用chunkへの参照、専用metadata依存が残らない。単に表示をCSSで隠した状態を削除完了としない。
- 1440pxのPCと390pxの狭幅、明暗で代表記事を表示し、本文と通常の目次が使える。Mermaid、数式、keyboard、検索、音声、ロードマップの依存グラフが維持される。
- unitとbrowserは削除後の必要な試験を実行する。廃止する機能の旧試験を残して失敗させたり、共有試験を丸ごと消して合格にしたりしない。
- PRとmainの必須CI、Pages公開を区別して確認する。公開後は代表ページと通常の目次・既存図の表示のみ確認する。

現在のmain CIはnpm auditで失敗している。機能削除だけで依存監査が解決するとは扱わず、実施時に失敗内容を確認する。必須CIの成功に必要な依存修正が残れば、削除差分とは理由を分けて最小限に扱う。監査や保護ルールを無効化する案にはしない。

## 8. 将来の復元手順

### 保存当時の状態を取り出す

1. 私有バックアップを新しいフォルダへ取得し、bundleを検証する。
2. 独立cloneを作り、復元したい保存点をcheckoutする。
3. 元の未コミット状態が必要なら、RESTOREに従って元HEADへbinary patchと未追跡ファイルを戻し、記録したstatus/indexと比較する。現行の作業ツリーへ上書きしない。
4. ソースからのbuild、または保存済み静的サイトのHTTP表示を行う。保存点と動作確認した範囲を報告する。

### 運用するサイトへ戻す

削除直後で本文・共有実装に変更がなければ、削除commitのrevertを通常PRで検証する方法が候補になる。ただし、それで戻るのは削除PRに含まれたmainの機能であり、未マージのP4/P5まで自動復元するものではない。

その後に記事やサイトを更新した場合、最新mainから再導入用PRを作り、選んだ保存点の図解部品と必要な共有接続を戻す。記事の原文対応・安全性・必要な受入検査を取り直す。旧mainへresetしたり、古いMDXで新しい本文を置き換えたりしない。
