## 静的棚卸し

全199本文・422 PNGを各1回集計し、最初の画面計測の対象を絞った。以下はデータ量・寸法の棚卸しであり、描画時間や常駐メモリの測定ではない。

| 対象 | 負荷の根拠 | 残す画面計測 |
| --- | --- | --- |
| モデル選定 | 最大PNG 2976×3819、RGBA32換算45,461,376 bytes／枚 | 大図の初回表示・拡大・テーマ変更とpeak memory |
| Transformer | 78 top-level blocks、行内数式84回、片テーマ65 PNG | スクロール、文字サイズ・テーマ変更、復帰 |
| OpenAI prompting | 最大本文JSON 129,569 bytes、recursive 169 blocks | 長文と階層リストの表示・読書位置保存 |
| コーディングエージェント比較 | 最大表は見出し込み135セル | 最大文字・横移動・読み上げ |
| 構造化出力 | 最大コード31行・1,636 bytes | 横移動・コピー |
| 全記事一覧 | search_textのUTF-8合計2,359,639 bytes | 初回表示と入力から検索結果までの時間 |

画像cacheは64MiB・96件のNSCacheで、厳密な常駐メモリ上限ではない。全422 PNGのRGBA32単純合計は約2.10GBだが、全画像を同時にロードした値ではない。幅6756×1020と高さ1488×4824の図も、全記事の画面確認に含める。

## 変更と検証

`LibrarySearch.matches`は空の語句でも記事全文を正規化してから空配列の`allSatisfy`を評価していた。正規化した語句が空なら先に`true`を返す1行だけを追加し、従来と同じ結果を得る。通常のAND検索・filter・記事順・保存には変更しない。

実199記事・15queryで、変更前後の一致IDと順序がすべて同じだった。大小・全半角・カナの同義4組も一致した。通常CoreSmokeは3記事・音声1本・140ファイルで成功し、独立レビューで1行差分・source SHA・生の結果JSONと中央値を再照合した。

macOS 14.6.1 arm64、CLT Swift 5.8.1の`-O -whole-module-optimization`、warmup1回後に各3回計測した。199記事のfilter/map中央値は空queryが128.469875msから0.15525ms、空白が128.3575msから0.296959ms、全角空白が128.31125msから0.272458msだった。baseline→candidateの順で実行し、decode・検証・本文読込・UIは計測外である。[JSON](ios-empty-search-performance.json)に条件と結果を残す。

初回起動、非空検索の入力応答、スクロール、画像decode・メモリ、実機の目標値と画面受入は未完了であり、IOS-15を完了としない。新しい性能閾値は追加しない。
