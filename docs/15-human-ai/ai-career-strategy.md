# AI 時代のエンジニアキャリア戦略

## この記事の目的

「AI に置き換えられるのでは」という漠然とした不安を、**根拠のある個人戦略** — 何を深め・何を任せ・何で価値を出すか — に変換できるようになります。将来の雇用を予測するのではなく、**価値の重心がどこへ移るか**という構造と、そこから導ける選択肢を整理します。

**本記事は、ライブラリの中で最も意見が分かれやすいテーマです。** 特定の職種の消滅や年収の予測といった**断定的な将来予測はしません**。構造と選択肢を示し、判断は読者に委ねます。

## 対象読者

- AI の進展に、キャリアの不安と関心の両方を持つエンジニア
- チームメンバーのキャリア相談に、ハイプでなく構造で応えたいリード・マネージャー

## 前提知識

- [AI Agent プロフェッショナルのスキルマップ](../00-overview/skill-map.md) — 深める領域を考える土台(本記事はその個人キャリア版)
- 特別な前提はありません

## 本文

### 概要: 予測ではなく、価値の重心で考える

キャリアの議論は「AI が仕事を奪うか否か」に流れがちですが、それは予測の問題で、誰にも確実には分かりません。より実用的なのは、**自分の仕事で何が変わり、どの技能が必要か**を観測して、投資先を決めることです。本記事の分類は学習投資の設計案であり、将来の雇用や賃金を予測するものではありません。ここでは 3 つの問い — 何を任せ、何を深め、何で価値を出すか — に落とします。

### 自分の業務で変化を確認する

[OECD の AI と技能に関する整理](https://www.oecd.org/en/publications/oecd-employment-outlook-2023_08785bba-en/full-report/skill-needs-and-policies-in-the-age-of-artificial-intelligence_fe530fbf.html)は、仕事の変化に応じた技能・研修の必要性を扱います。ただし、特定技能の市場価値がすべての職種で同じ方向へ動くとは限りません。自分の業務では、次を確認します。

- **コードや文章の生成**を任せたとき、仕様確認・手直し・検証を含む総所要時間と品質がどう変わるか
- **仕様化・検証・判断・結果への対応**のどこに負担が残り、技能を足すと改善するか
- これは本ライブラリ全体の主張とも一致します — [PoC から本番への進め方](../09-business/poc-to-production.md)・[評価](../04-evaluation/agent-evaluation-basics.md)・[Human-in-the-Loop](../02-architecture/human-in-the-loop.md) が扱う「作った後」の作業も、学習候補として点検します

本記事では、生成速度だけでなく、**要求を定義し、成果を検証できること**も実績として記録することを提案します。

### 深める領域の選び方

すべてを深めることはできません。[スキルマップ](../00-overview/skill-map.md)の領域を、**市場価値と希少性**の軸で個人向けに読み直します。

- **継続して深める候補**: 原理の理解(なぜそう動くか)、ドメイン知識(業務・制度の深い理解)、設計判断・アーキテクチャ、検証・品質保証、対人・調整(要件を引き出す・合意を作る)
- **委譲を試して効果を測る候補**: 定型的な生成、暗記で足りる知識、手順が決まった作業
- **自分の掛け算を作る**: 「AI が得意な生成」× 「AI が苦手なドメイン・判断・対人」の交点に、個人の希少性が生まれやすい

どれが正解かは人・市場で変わります。**「AI が肩代わりしにくく、自分が伸ばせて、需要がある」の重なり**を各自で見つけるのが、汎用の指針です。

### 「AI を使いこなす」の中身

「AI を使いこなせる人が生き残る」とよく言われますが、その中身は**道具の操作習熟を超えています**。

- **委譲の設計**: どのタスクを、どこまで任せ、どう成果を受け取るかを設計する能力([Workflow 型 vs Agent 型の使い分け](../02-architecture/workflow-vs-agent.md)の個人版)
- **検証の設計**: 任せた結果の正しさを、続けられる形で担保する能力([AI 出力の検証習慣](verifying-ai-outputs.md))
- **過信しない自制**: 任せきって技能や判断力を失わないバランス([オートメーションバイアスとスキル退化](automation-bias-and-deskilling.md))

つまり「プロンプトが上手い」より、**「委譲と検証と判断を設計できる」**ことが、使いこなしの実体です。

### 実績の示し方

AI を使った成果物でも、**何を作り、どこを自分が判断したか**を説明できる形にします。

- 動くデモに加え、対象ユーザー・実行条件・確認済みの範囲を示します
- 代わりに、**難しい判断をした過程・品質を担保した方法・失敗から学んだこと**が、実力の証明になります
- ポートフォリオも「何を作ったか」に加えて「なぜその設計にしたか・どう検証したか」を語れると強い

### 陳腐化への備え

技術の陳腐化に対して、本記事では**原理の理解も投資先に含める**ことを提案します。

- フレームワークや特定モデルの使い方は速く変わります。一方、[Agent ループ](../01-concepts/agent-loop.md)・[LLM の能力と限界の由来](../10-llm-foundations/capabilities-and-limits.md)といった原理は変わりにくい
- これは本ライブラリが「概念(01)・LLM 基礎(10)を飛ばすな」と繰り返す理由でもあります([学習ロードマップ](../00-overview/learning-roadmap.md))
- 具体技術は「今使うために」学び、原理は「長く効かせるために」学ぶ、という二層で投資すると減価しにくくなります

### ハイプとの付き合い方

キャリアの話題は煽られやすく、予測の根拠・対象職種・期間を確認する必要があります。

- 「N 年で職種 X が消える」式の予測は、根拠が弱いまま不安を煽ります。真に受けて極端な行動を取らない
- 一方で「何も変わらない」という否認も危険です。**自分の業務や求人の変化を観測し、単一の予測に依存しない**のが健全です
- 焦って表面的なスキルを追うより、重心移動に沿って**判断・検証・原理**へ投資する方が、多くの将来シナリオで効きます

## 実務での注意点

### アンチパターン

- **「AI に奪われる/奪われない」の二択で考える** → 予測に賭けて極端な行動を取る、または否認して備えない → 「価値の重心がどこへ移るか」の構造で考え、判断・検証・原理へ投資する
- **生成の速さだけを磨く** → 要求定義や品質確認など、他の技能が不足する場合がある → 仕様化・検証・判断・責任という重心側を厚くする
- **「プロンプトが上手い = 使いこなし」と捉える** → 道具の操作に矮小化し、委譲・検証の設計力が育たない → 委譲と検証と判断の設計を「使いこなし」の中身と捉える
- **原理を飛ばして流行の道具だけ追う** → 陳腐化が速く、投資が短命に終わる → 原理(01・10 章)への投資を長期の軸に据える
- **断定的なキャリア予測を鵜呑みにする** → 根拠の弱い予測に振り回される → 構造の変化は認め、具体の予測には距離を置く

### チェックリスト

- [ ] 単一の予測に依存せず、自分の業務と需要の変化を観測している
- [ ] 深める領域を、AI が肩代わりしにくさ・自分の伸びしろ・需要の重なりで選んでいる
- [ ] 「使いこなし」を、委譲・検証・判断の設計能力として捉えている
- [ ] 実績を「作れる」でなく「どう判断し・どう担保したか」で示せる
- [ ] 原理(01・10 章)への投資を、具体技術と別枠の長期軸に置いている
- [ ] 断定的なキャリア予測に距離を置きつつ、構造の変化には備えている
